Problem Statement & Objective

The Why

Executive Summary

SubSense is an AI-assisted subscription decision platform for individuals and small shared groups. It helps users understand recurring subscription spending, receive contextual renewal reminders, manage shared subscription payments, and make informed renewal decisions. The product focuses on awareness and decision support, not direct subscription control.

Current Problem

Modern users pay for recurring subscriptions across entertainment, productivity, AI tools, education, cloud services, fitness, and memberships. Because these payments renew automatically, awareness breaks down long before the decision ever gets made.

Awareness gaps
  • Users forget renewal dates
  • Users underestimate annual spending
  • Duplicate or overlapping services go unnoticed
Decision gaps
  • Shared subscription payments become difficult to track
  • Cancellation decisions are delayed until after renewal
  • Existing tools mostly report spending after the fact

Vision

Build the most trusted AI-assisted subscription decision platform that helps users understand recurring spending, stay informed before renewals, and make confident subscription decisions without taking control away from them.

Mission

Help users become aware of recurring subscription spending through timely reminders, financial context, and AI-assisted decision support — while ensuring users always remain in control of renewal, cancellation, sharing, and payment decisions.

Value Proposition

  • What am I paying for?
  • What renews soon?
  • How much does this cost me annually?
  • Is this subscription still worth reviewing?
  • Who owes what for shared subscriptions?
  • What should I pay attention to today?

Product Principles

  • User control first
  • Decision support over automation
  • Workflow first
  • Explainable AI
  • Savings before spending
  • MVP discipline
  • Email-first communication
  • Decision support, never decision execution

The Score

Two decisions define this scorecard. DEC-040 measures activation and correctness — seven metrics covering onboarding, delivery, AI quality, and error rate. DEC-041 adds an eighth metric that none of the first seven capture: whether a user stays. Together they form a numeric pass/fail bar, not a task checklist, frozen alongside 01_Product_Strategy.

Retention context: renewal-triggered reminders alone leave a gap — a user with one or two subscriptions on far-apart renewal dates could go months without an email and have no reason to open SubSense. A monthly digest (sent to every user with a non-archived subscription, independent of renewal date) and a single lapsed-user re-engagement email (triggered past 45 days inactive, capped at one per rolling window) close that gap using the existing reminder infrastructure rather than a new subsystem, per GP-007 Reuse Before Creation. The 40% Day 30 target is directional for a capstone-scale MVP, not a benchmarked figure.

Guardrails

The How We Stay Honest

Key risks

  • AI overreach — mitigated by enforcing BR-001 in backend and frontend copy
  • RLS mistakes — mitigated by testing owner/member/admin access paths
  • Scope expansion — mitigated by MVP scope discipline and change control
  • Defects found too late — mitigated by the Phase 9.5 mid-build stress checkpoint (DEC-033)
  • Payment confusion — mitigated by labeling Razorpay as Test Mode everywhere

Explicitly out of scope (v1)

  • Automatic bank account or email scanning
  • Apple/Google subscription sync
  • Automated third-party cancellation execution
  • Production billing / live Razorpay payments
  • Browser extension, mobile app, enterprise administration

Core Business Rules

BR-001AI never performs user actions.
BR-002Only authenticated users may access subscription data.
BR-006First login automatically provisions a user profile.
BR-007Returning users must not create duplicate profiles.
BR-008Authentication must complete before loading user-specific data.

Governance Principles

GP-001User Control First — users retain final control over financial decisions.
GP-002Decision Support Over Automation — AI supports decisions but never executes.
GP-003Simplicity Before Features — every feature solves a real user problem.
GP-006Architecture Before Features — structural decisions stabilize before scope expands.
GP-007Reuse Before Creation — existing patterns are reused before new ones are created.

Dependencies & assumptions

  • Users are willing to manually enter subscriptions without bank/email auto-import Assumption
  • AI model can produce high-confidence renewal insight from manually entered data alone Assumption
  • Email-first reminders (no push/mobile app) are sufficient for MVP engagement Assumption
  • Razorpay Test Mode is an acceptable substitute for live payment validation in this capstone context Assumption

Path A — Direct Data Access

The frontend uses the Supabase client (supabase-js) directly for user-owned CRUD: profile, preferences, subscriptions, shared subscriptions, members, payment requests, and reads of reminders/notifications/AI output/catalog. Row Level Security is the enforcement layer — RLS stands in for a Repository/Service layer for these simple, owner-scoped operations.

Path B — Edge Function APIs

Supabase Edge Functions using the service-role key handle anything touching a provider secret (OpenAI, Resend, Razorpay), anything running on a schedule, and any write to system-owned tables (ai_recommendations, notifications, reminder_history, audit_logs, payment_transactions).

This is DEC-031's Lean Access Architecture: two access paths rather than one uniform pipeline, sized to match solo/part-time build capacity without loosening enforced business rules. Across both paths: the frontend never talks directly to OpenAI, Resend, or Razorpay; provider keys and the service-role key never reach the frontend; JWT is the trust boundary for both paths; Supabase remains the single system of record.
