## Purpose

This document defines exactly how the SubSense frontend accesses data and business logic. It replaces the earlier placeholder skeleton with a real, buildable contract, expressed in the **Lean Access Architecture** (Decision Log entry DEC-031 below): direct Supabase client access under Row Level Security for standard data operations, and dedicated Edge Functions only where a provider secret or cross-cutting business computation is involved.

This document does not change product scope, screens, entities, or business rules defined in documents 00-10. It defines *how* those already-frozen rules are technically enforced.

**Note on Depends On:** 01 and 03 were added because this document already cited them substantively (Authentication method per 01, Reminder Strategy's six reminder types per 01, Developer/Test Utilities routing per 03) without declaring them — a documentation-completeness gap, not a content change. 12_Backend_Architecture is declared as a dependency in both directions: this document's response envelope and error-object formats (Sections 2 and 7) are defined in 12's Standard Response Contract, and 12's Backend Layer Model in turn depends on this document's Section 1 Path A/Path B routing rule. ## 1. Access Architecture Overview

Two access paths exist. Every table and every capability in SubSense is assigned to exactly one.

| Path | Mechanism | Used For |
| --- | --- | --- |
| A — Direct Data Access | Supabase client (`supabase-js`) from the frontend (built in Cursor, DEC-053), governed entirely by RLS policies from `10_Database_Architecture_v1.22` | All user-owned CRUD: profile, preferences, subscriptions, shared subscriptions, members, payment requests, reading reminders/notifications/AI output/catalog |
| B — Edge Function APIs | Supabase Edge Functions, using the service role key, never exposed to the frontend | Anything touching OpenAI, Resend, or Razorpay secrets; anything that must run on a schedule; anything writing to system-owned tables (`ai_recommendations`, `notifications`, `reminder_history`, `audit_logs`, `payment_transactions`) |

Rule of assignment: **if a table is only ever read or written by its owning user, it is Path A. If a write requires a provider secret, a cron trigger, or must never be user-editable, it is Path B.**

## 2. API Standards (applies to Path B only; Path A follows Supabase's native contract)

- JSON request and response bodies.
- All Edge Functions require a valid Supabase JWT in the `Authorization` header, verified before any logic runs.
- Dates in ISO 8601. Currency values as decimal, currency code separate (`INR` / `USD`).
- Every Edge Function response follows the standard envelope defined in `12_Backend_Architecture_v1.15`:

```json
{ "success": true, "data": {}, "meta": {} }
```
```json
{ "success": false, "error": { "code": "ERROR_CODE", "message": "User-safe message" } }
```

- Idempotency keys are required on `razorpay-verify-payment` and `send-reminder-email` to prevent duplicate financial or email side effects on retry.

## 3. Authentication and Authorization

Authentication: Supabase Auth, Google Sign-In primary, email/password fallback, per `01_Product_Strategy_v1.19`.

Provisioning (implements BR-006, BR-007): a Postgres trigger `handle_new_user()` fires on `auth.users` insert and creates the corresponding `users`, `user_profiles`, and `user_preferences` rows in one transaction. This guarantees profile provisioning happens exactly once, at the database layer, with no custom API code and no possibility of a duplicate-profile race condition.

Authorization for Path A is enforced entirely by RLS policies already specified per-table in `10_Database_Architecture_v1.22`. Authorization for Path B is enforced by each Edge Function validating the caller's JWT `sub` (user id) against the resource being acted on before using its service-role privileges.

Developer/Test Utilities (`03_Information_Architecture_v1.17`) call the same Path B functions as normal usage — there is no separate "test" code path, only a restricted route that is allowed to trigger them on demand instead of waiting for a schedule or user action.

## 4. Path A — Direct Data Access Catalogue

For each resource: allowed client operations, and which RLS policy (already defined in doc 10) governs it.

| Resource (table) | Client Operations | Governing RLS | Business Rule Enforced |
| --- | --- | --- | --- |
| `user_profiles` | select, update (own row) | Owner only | Profile module ownership |
| `user_preferences` | select, update (own row) | Owner only | Reminder default configuration |
| `subscription_categories` | select | Authenticated read, admin write | Master data read-only |
| `subscription_catalog` | select | Authenticated read, admin write | Catalog search in Add Subscription |
| `subscriptions` | select, insert, update, soft-delete (`archived_at`) | Owner only | BR-002; Archive-first (EXP-007); DEC-032 payment rail awareness |
| `shared_subscriptions` | select, insert, update | Owner only | Sharing Strategy |
| `shared_members` | select, insert, update, soft-remove | Owner of parent `shared_subscriptions` | Preserve payment history on member removal |
| `payment_requests` | select, insert, update status | Owner: any valid transition. Linked member: `pending -> paid_pending_confirmation` only (DEC-037) | Payment status tracking |
| `reminders` | select | Owner only, insert/update system-only | Reminder visibility without user tampering |
| `reminder_history` | select | Owner only, append-only, no client write | Immutable execution record |
| `ai_recommendations` | select | Owner only, no client write | BR-001: AI output is read-only to the user who receives it |
| `notifications` | select | Owner only, no client write | Delivery record integrity |
| `premium_plans` | select | Authenticated read, admin write | Plan comparison in Profile |
| `payment_transactions` | select | Owner only, no client write | Financial record integrity |
| `audit_logs`, `system_settings` | none | No client access at any level | System/security isolation |

**Calculated fields** (`monthly_equivalent`, `annual_equivalent` on `subscriptions`): computed by a Postgres function `calculate_subscription_equivalents()` invoked as a `BEFORE INSERT OR UPDATE` trigger, so the database is always the authoritative value. The frontend's Annual Cost Preview (component C-011) mirrors the same formula client-side purely for live-typing feedback before save; the saved value always comes from the trigger, not the client calculation. This keeps DEC-024 (single source of truth for business data) intact.

**Reminder generation** (DEC-039, full column/constraint detail in `10_Database_Architecture_v1.22`): the six reminder types in `01_Product_Strategy_v1.19` Reminder Strategy are generated by three different mechanisms, not one:

- `seven_day`, `two_day`, `renewal_day`: a trigger on `subscriptions` insert/update calls `generate_default_reminders()`, which reads the user's `reminder_default_days` from `user_preferences` and the user's `user_profiles.timezone`, and creates the corresponding rows in `reminders` with `scheduled_for` computed in that timezone. This is the "Reminder Service" from doc 12, implemented as a database function rather than an application-layer class.
- `post_renewal_checkin`, `monthly_digest`, `lapsed_reengagement`: generated by `generate-scheduled-reminders` (5.7 below, DEC-068), a single Supabase Cron job running once daily, evaluating all three conditions in one run since each is a day-granularity event that does not need hourly evaluation. Closes the gap where these three promised reminder types previously had no concrete generation mechanism named (only "a scheduled Path B function," and `monthly_digest`/`lapsed_reengagement` were not mentioned in this section at all).
- `shared_payment`: created when a `payment_requests` row is created, and re-sendable on demand via 5.3 below.

**Due-today evaluation** (query logic completed under DEC-068): `send-reminder-email` (5.2) runs hourly via Supabase Cron and selects `WHERE status = 'pending' AND scheduled_for <= now()`. Since `scheduled_for` is already an absolute UTC instant computed from each reminder's own `timezone_snapshot` at generation time, this direct instant comparison is equivalent to, and simpler than, evaluating a UTC day boundary per timezone — a user in `Asia/Kolkata` is still not evaluated against the wrong calendar day, because that timezone was already baked into `scheduled_for` when the row was generated. The `<= now()` (not `= now()`) comparison also makes the job self-healing: it catches up on any reminder whose `scheduled_for` has passed, including after a skipped or delayed cron tick, with no dedicated retry system required — a reminder is only set `status = 'sent'` after Resend confirms delivery, never optimistically before the call, so a mid-run failure simply leaves it `pending` for the next tick. Active alerting/monitoring on missed cron ticks themselves is out of MVP scope, tracked in `NEXT_SESSION_AGENDA.md` for production scale.

**Archived subscriptions**: a trigger sets any still-`pending` reminder to `status = 'skipped_archived'` when its parent subscription is archived, so the cron job never sends a reminder for a subscription the user has already archived.

## 5. Path B — Edge Function Catalogue

### 5.1 `POST /functions/v1/ai-generate-insight`

- **Purpose:** Implements the AI Insight Service. Generates an AI Decision Card / AI Insight for one subscription or the full Decision Workspace batch.
- **Auth:** Required. Caller must own the subscription(s) requested.
- **Request:** `{ "subscription_id": "uuid" }` or `{ "scope": "workspace" }`
- **Behavior:** Loads subscription metadata, renewal schedule, billing frequency, lifecycle status, shared status (per AI Information Flow, doc 03). Calls OpenAI. Writes result to `ai_recommendations` using the service role key. Creates an `audit_logs` entry.
- **Response:** Wrapped in the standard envelope (Section 2/`12_Backend_Architecture`), like every other Path B endpoint — success shape depends on the request. For `{ "subscription_id": "uuid" }`: `{ "success": true, "data": { "recommendation": "...", "reason": "...", "financial_impact": {...} }, "meta": {} }`. For `{ "scope": "workspace" }`: `{ "success": true, "data": { "insights": [{ "subscription_id": "uuid", "recommendation": "...", "reason": "...", "financial_impact": {...} }, ...] }, "meta": {} }` — `insights` holds up to 3 entries (DEC-079's Critical/Upcoming urgency cap) for a premium user, or exactly 1 (the single highest-urgency subscription) for a free-tier user — per DEC-082/DEC-083's gating rule, checked server-side via `user_has_active_premium(uuid)` (RPC to the existing `security definer` SQL function, never a client-supplied premium flag) — one per subscription selected server-side; an empty `insights` array is a valid 200 response when no subscription currently qualifies, not an error. This split — a flat `data` object for single-subscription requests, an `insights` array inside `data` only for the batch case — was confirmed in Phase 7 implementation planning (DEC-079 same-day extension, doc 08 v1.52), mirroring `send-reminder-email`'s (5.2) own precedent of varying response behavior between batch and single mode. The envelope wrap itself was a same-day implementation-time correction: an earlier draft of this section (still bare, unwrapped) was inconsistent with Section 2's universal envelope rule — caught and fixed before any frontend code was built against it.
- **Never:** writes to `subscriptions`, `shared_subscriptions`, or any table other than `ai_recommendations` and `audit_logs` — this is the literal enforcement point for BR-001 and GP-002.
- **Errors:** `AI_001` provider timeout, `AI_002` invalid subscription ownership, `AI_003` generation failed (fallback: Decision Workspace shows a neutral "insight unavailable" state, never a blocking error). For `{ "scope": "workspace" }`, one subscription's failure within the batch does not fail the whole call — that subscription is simply omitted from `insights`, and the frontend treats a missing entry as "unavailable" for that one card, not a page-level error.

### 5.2 `POST /functions/v1/send-reminder-email` (scheduled, hourly)

- **Purpose:** Implements the Notification Service for renewal reminders. Invoked hourly by Supabase Cron (platform choice formalized under DEC-068), evaluating `WHERE status = 'pending' AND scheduled_for <= now()` per the Due-today evaluation logic in Section 4.
- **Auth:** Service-role only; not callable by the frontend directly. Developer/Test Utilities call it through 5.4 instead.
- **Behavior:** Selects due reminders, renders the matching `notification_templates` row, calls Resend, writes `notifications` (delivery status) and `reminder_history` (append-only, immutable per doc 10). Only sets `reminders.status = 'sent'` after Resend confirms delivery — never optimistically beforehand — so a mid-run failure leaves the row `pending` for the next hourly tick to retry, and a skipped or delayed cron tick self-heals on the next successful one. No separate retry/fallback system exists beyond this query behavior (DEC-068); active cron-failure alerting/monitoring is deferred past MVP.
- **Idempotency:** keyed on `reminder_id` + scheduled date, so a retried cron run cannot double-send.
- **Errors:** `NOTIF_001` template missing, `NOTIF_002` provider delivery failure (retried up to 3 times within the same invocation, then logged to `audit_logs` and left `pending` for the next hourly tick).

### 5.3 `POST /functions/v1/send-shared-payment-reminder`

- **Purpose:** User-triggered variant of 5.2 for a specific `payment_requests` row (Shared Subscriptions "Send Reminder" action).
- **Auth:** Required. Caller must own the parent `shared_subscriptions` row.
- **Request:** `{ "payment_request_id": "uuid" }`
- **Behavior/Errors:** same as 5.2, scoped to one request.

### 5.4 `POST /functions/v1/dev-trigger`

- **Purpose:** Single restricted entry point behind Developer/Test Utilities that invokes 5.1, 5.2, or a Razorpay test transaction on demand, for capstone validation.
- **Auth:** Required, and gated by the Developer/Test Utilities route protection defined in `03_Information_Architecture_v1.17`.
- **Request:** `{ "action": "send_reminder_now" | "test_ai" | "test_email" | "test_payment", "target_id": "uuid" }`
- **Rule:** exposes no secrets in its response; returns only status and the same payload shape the real flow would produce.

### 5.5 `POST /functions/v1/razorpay-create-order` — Built (DEC-083)

- **Purpose:** Implements the Billing Service order-creation step for the premium demonstration flow.
- **Auth:** Required.
- **Request:** `{ "plan_code": "..." }` — never client-supplied amount or currency; both are looked up server-side from the matching `premium_plans` row (`is_active = true` only).
- **Behavior:** Creates a Razorpay Test Mode order for the selected `premium_plans` row via a plain `fetch` call to Razorpay's Orders API (Basic Auth, no SDK — the `razorpay` npm package has no Deno build). Returns the order id and test-mode client key needed for Razorpay's checkout widget. Never returns the Razorpay secret key. Inserts a `payment_transactions` row (`status: "created"`) before responding — an order with no local transaction row would be unverifiable and non-idempotent later. Receipt format: `"sub_" + Date.now() + "_" + userId.slice(-8)` (≤40 characters, Razorpay's receipt limit — a naive full-UUID receipt would exceed it).
- **Response:** `{ "order_id": "...", "amount": ..., "currency": "INR", "key_id": "test_..." }`
- **Errors:** `PAY_004` — plan not found or inactive (kept distinct from PAY_002's "order not found" meaning in 5.6, rather than overloading one code across two functions with different meanings).

### 5.6 `POST /functions/v1/razorpay-verify-payment` — Built (DEC-083)

- **Purpose:** Implements payment verification. Called after the Razorpay Test Mode checkout completes client-side.
- **Auth:** Required.
- **Request:** `{ "razorpay_order_id": "...", "razorpay_payment_id": "...", "razorpay_signature": "..." }`
- **Behavior:** Verifies the signature server-side (HMAC-SHA256 via Web Crypto, no network call) against the Razorpay secret (never sent to the client). On success, uses a compare-and-swap conditional update (`WHERE razorpay_order_id = ... AND status = 'created'`) to flip the transaction to `verified`, then sets `user_profiles.is_premium = true`, `premium_expires_at`, and `premium_source = 'razorpay_test_mode'` (DEC-038 — the single premium entitlement source of truth; no other table stores current entitlement state). `premium_expires_at` is computed from the transaction row's own immutable `verified_at` (set exactly once, at the moment status first flips) plus the plan's `duration_days` — deliberately never from wall-clock `now()` at call time, so every replay of this same call (a genuine duplicate callback, or a concurrent race) converges on the identical fixed expiry rather than letting a resent success payload push it out further each time. If the conditional update loses a concurrent race (0 rows affected), the transaction row is re-selected and the response branches on its actual committed state (verified with a matching payment id grants; verified with a different payment id, or failed, does not) rather than assuming success. On signature mismatch, writes a failed transaction record and returns a user-safe error.
- **Idempotency:** keyed on `razorpay_payment_id` — a duplicate verification call for an already-verified payment with the same payment id returns the existing result rather than double-crediting premium status. A different payment id against an already-verified order is treated as a tamper/replay anomaly, not a normal error path, and is logged to `audit_logs` before the error response.
- **Errors:** `PAY_001` signature mismatch, `PAY_002` order not found or not owned, `PAY_003` already verified (idempotent success, not an error to the user), `PAY_005` upstream Razorpay/DB failure.

### 5.7 `POST /functions/v1/generate-scheduled-reminders` (scheduled, daily)

- **Purpose:** Implements row generation for the three reminder types that cannot be created by the `subscriptions`-table trigger: `post_renewal_checkin`, `monthly_digest`, `lapsed_reengagement` (DEC-068, completing the generation-mechanism gap left open in Section 4 and in `10_Database_Architecture_v1.22`).
- **Auth:** Service-role only; not callable by the frontend directly. Developer/Test Utilities do not currently expose a trigger for this function (row generation is not a demo-relevant action the way sending a reminder is).
- **Invoked by:** Supabase Cron, once daily. A daily cadence is sufficient because all three conditions it evaluates are day-granularity (a subscription's renewal date, a calendar month, a 45-day login threshold), not hour-granularity.
- **Behavior:** In one run, evaluates: (1) subscriptions whose `next_renewal_date` was exactly 3 days ago, inserting a `post_renewal_checkin` row at 9am in the user's `user_profiles.timezone` (DEC-039/047); (2) every user with at least one non-archived subscription who does not already have a `monthly_digest` row for the current calendar month, inserting one (DEC-041); (3) every user whose `users.last_login_at` exceeds 45 days who does not already have a `lapsed_reengagement` row within the current rolling 45-day window, inserting one (DEC-041). Duplicate prevention for all three follows `10_Database_Architecture_v1.22`'s existing constraints (the partial unique index for `post_renewal_checkin`; the generating-job existence check for `monthly_digest`/`lapsed_reengagement`).
- **Errors:** `GEN_001` — a per-user insert failure (e.g. a constraint violation) is logged to `audit_logs` and does not abort the run for other users; the next day's run re-evaluates that user from scratch since generation checks current state, not a queue.

### 5.8 `POST /functions/v1/insights-generate-summary` — Built (DEC-083)

- **Purpose:** Implements the premium-exclusive Phase 9 Insights page content: a per-currency spend summary, duplicate/category-overlap detection, an intra-portfolio cost comparison, and one AI-written summary paragraph framing the deterministic figures.
- **Auth:** Required. Premium-gated as a hard server-side boundary (`user_has_active_premium(uuid)` via RPC) — RLS has no premium concept, so this check is the real gate, not the frontend's client-side skip.
- **Request:** none beyond auth (operates over the caller's own active subscriptions).
- **Behavior:** Computes spend totals per active currency, exact/category-overlap duplicate detection, and a category-average cost comparison entirely from the caller's own portfolio — no competitor or market-pricing data exists anywhere in this schema, so no such claim is invented. The response's cost-comparison field is named `cost_comparisons` (type `CostComparisonItem`, computed via `findCostComparisons` — renamed from `lower_cost_alternatives`/`LowerCostAlternative`/`findLowerCostAlternatives` under DEC-085, a coupled Edge-Function-and-frontend wire-contract change, to correct the original name's overpromise that a competitor/market-cheaper option exists). The currency-total lead sentence is built server-side by direct string templating from `spendSummary`, not by the model (DEC-085) — e.g. "You're spending ₹868.00 and $9.00 across 4 active subscriptions this month," single-currency portfolios using the same pattern with one figure. Exactly one OpenAI call frames the already-computed deterministic facts in a short qualitative sentence appended after the templated lead; the model never computes or restates a figure itself, matching `ai-generate-insight`'s existing `financial_impact` discipline. Enforced at the code level, not just by prompt instruction: if the model's returned framing text matches `/\d/` or contains `₹`/`$`, it is discarded and replaced with a static fallback sentence, since a prompt instruction alone was judged insufficient given this is the exact bug the templating approach was built to fix. No caching — computed fresh on every page load, since only premium users can reach it (bounded cost).
- **Errors:** `INS_001` not premium (403).

## 7. Error Catalogue

Standard error object (matches `12_Backend_Architecture_v1.15`):

```json
{ "success": false, "error": { "code": "SUB_001", "message": "Validation failed" } }
```

| Code Family | Meaning |
| --- | --- |
| `AUTH_xxx` | Session/authorization failures (Path A surfaces these as native Supabase auth errors) |
| `SUB_xxx` | Subscription validation (name required, cost positive, currency INR/USD, valid billing frequency, valid payment_method) |
| `SHR_xxx` | Sharing/member/payment-request validation |
| `AI_xxx` | AI generation failures (5.1) |
| `NOTIF_xxx` | Email delivery failures (5.2, 5.3) |
| `PAY_xxx` | Order-creation and payment-verification failures (5.5, 5.6) — `PAY_004` plan not found/inactive, `PAY_005` upstream Razorpay/DB failure, plus `PAY_001`-`003` (5.6, see Section 5.6) |
| `INS_xxx` | Insights summary access failures (5.8) — `INS_001` caller is not premium (403) |
